# CLAUDE.md：关于如何让语言模型写出你不必重写的代码的实地考察笔记

一份简短的规则清单，诞生于反复目睹相同错误之后的教训

Andrej Karpathy

**摘要。** 这份文档的存在，是因为语言模型在编写代码时会犯下可预测的错误。不是随机错误，而是相同的错误一遍又一遍地出现，频繁到值得将其记录下来。以下内容并非一套建议，而是一套规则。贯穿每一部分的共同主题是：模型生成看似合理的代码很快，但注意到“合理”并不等同于“正确”很慢，因此纪律必须来自围绕它的流程。

**关键词。** LLM辅助编程、代码审查、软件工艺、最小化差异、调试、依赖卫生。

## 1. 先阅读，再编写

糟糕的模型生成代码的最大来源是在阅读代码库之前就开始编写。阅读你要修改的文件；阅读，而不是略读。复制已存在的模式，并检查导入项，以了解项目实际依赖什么，这样你就不会在全是 fetch 的项目中伸手去拿 axios。当你找不到模式时，请询问，而不是猜测。

## 2. 先思考，再编码

在输入之前，先弄清楚你要做什么。陈述你的假设（“添加身份验证”意味着五种不同的事情，因此要说出你选择的那一种），并命名权衡。如果某事真正令人困惑，请停下来询问，而不是用看似合理的代码填补空白；这正是那种在粗略审查中通过、但在关键时刻失败的那种代码。

## 3. 简单性

编写能够解决当前问题的最小代码，而不是能够解决未来每一个愿景的最小代码。抵制过早抽象，跳过那些不会发生的错误处理，并硬编码值，直到有真正需要配置它们的理由。测试标准是：如果抽象某物的唯一原因是“以防我们需要”，那你就是过度设计了。

## 4. 外科手术式修改

你的代码差异（diff）应尽可能小。不要触摸你未被要求触摸的内容，匹配现有风格，不要重新格式化；格式化器的运行会将那三行重要的代码埋藏在三百行无关代码之中。测试标准是你能否用任务来证明每一行更改的合理性。如果某行代码是因为“反正我都在那儿”而存在的，那就撤销它。

## 5. 验证

能工作的代码和你以为能工作的代码之间的差距在于测试。修复 bug 时，先写失败的测试，看着它失败，然后修复它；这是你修复了原因而不是症状的唯一证明。测试那些实际会出错的行为，而不是构造函数是否设置了字段。如果某事很难测试，那是关于设计的信息，而不是跳过测试的理由。

## 6. 目标驱动的执行

每项任务都需要在编写代码之前有一个成功标准。“添加验证”变为“拒绝缺失或格式错误的电子邮件，返回带有清晰消息的 400 错误，并测试这两种情况。”对于任何多步骤任务，先陈述计划，这样用户才能在你花一个小时构建之前捕捉到错误的方法。

## 7. 调试

当事情出错时，进行调查；不要猜测。阅读整个错误和堆栈跟踪，在更改任何内容之前重现问题，一次只更改一件事。不要掩盖意外的空值检查；找出它为什么为空，否则 bug 只会转移到更安静的地方。

## 8. 依赖项

每个依赖项都是你无法控制的永久性代码。在添加一个之前，问问项目或标准库是否已经可以用 `crypto.randomUUID()` 代替 uuid 包来完成它。当你确实添加一个时，说出原因，这样选择就是可见的，而不是偷偷溜进清单中。

## 9. 沟通

说出你做了什么以及为什么，而不仅仅是一块代码。即使你完全按照要求做了，也要提出担忧，并精确地表达不确定性：“我不确定这个库是否支持流”告诉用户需要验证什么；“我认为这应该有效”则没有。

## 10. 常见故障模式

一些模式重复出现，足以被命名：厨房水槽（在你修改它时重构半个代码库），错误的抽象（在抽象之前复制粘贴两次），乐观路径（处理了快乐路径，忽略了 500 错误），以及失控重构（一个修复波及多个文件）。在任何一种情况下抓住自己，正确的做法是停下来，而不是继续推进。
